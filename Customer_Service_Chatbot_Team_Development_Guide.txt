CODEX PROMPT:

You are Member 1 implementing the Knowledge Ingestion module for our Customer Service Chatbot.

Read AGENTS.md completely and inspect the repository and src/models/ before coding.

My branch is feature/ingestion.

Work ONLY on the ingestion module. Use the existing KnowledgeDocument contract; do not create a duplicate.

Implement a modular pipeline supporting product documentation, FAQs, historical support tickets, knowledge-base articles, troubleshooting guides, and video transcripts.

Support loading, text cleaning/normalization, deterministic chunking with configurable chunk size/overlap, metadata extraction, product classification, issue type, severity, resolution category, version mapping, and output validation.

Preserve useful metadata on every chunk.

The output must be validated KnowledgeDocument objects suitable for Member 2's retrieval layer.

Do NOT implement OracleVS, embeddings, retrieval, conversation, proactive support, API/UI, or analytics.

Use interfaces/mocks for unavailable external dependencies.

Add tests for loading, cleaning, chunking, metadata preservation/extraction, invalid/empty documents, and deterministic output. Tests must not require OCI credentials or external services.

Run pytest -q, inspect git diff/status, and report files, architecture, tests, and integration assumptions.

5. MEMBER 3 — CONVERSATION ENGINE
============================================================

Branch:
feature/conversation-engine

Owns:
src/conversation/

Responsibilities:
- Multi-turn state
- Memory
- Context retention
- Intent handling
- Clarification
- Retrieval orchestration
- LLM context
- Troubleshooting tracking
- Resolution confirmation
- Escalation orchestration
- Confidence/fallback handling

CODEX PROMPT:

You are Member 3 implementing the Conversation Engine for our Customer Service Chatbot.

Read AGENTS.md completely. Inspect the repository and especially src/models/ before coding.

My branch is feature/conversation-engine.

Use the existing shared contracts. Do NOT create duplicate models.

Work ONLY on src/conversation/.

Implement conversation state management, memory, multi-turn context, intent handling, missing-information detection, clarification questions, retrieval orchestration, LLM response orchestration, troubleshooting-step tracking, resolution confirmation, escalation, and confidence/fallback handling.

Support a state flow similar to:
NEW → UNDERSTANDING → NEEDS_CLARIFICATION → READY_TO_RESOLVE → TROUBLESHOOTING → AWAITING_CONFIRMATION → RESOLVED

Also support UNRESOLVED → ESCALATED when appropriate.

The engine must retain context across turns and must not repeatedly ask for information already known.

Use a Retriever interface rather than accessing OracleVS directly:
retriever.search(query=..., filters=..., top_k=...)

Use the existing RetrievalResult.

Use an LLM interface rather than implementing another LLM infrastructure layer.

Track troubleshooting steps so failed/attempted steps are not blindly repeated.

Do not mark an issue resolved merely because a response was generated. Require user confirmation.

Consume the existing ProactiveAnalysis contract. Do NOT implement sentiment analysis.

Support escalation for explicit human-support requests, high frustration, repeated failed troubleshooting, high severity, unsupported issues, and low-confidence/no useful retrieval.

Do not hallucinate when retrieval is empty or low-confidence.

Create mocks/interfaces for dependencies that other team members have not implemented yet.

Add tests for context retention, clarification, no repeated questions, intent, retrieval integration, LLM integration, troubleshooting, resolution confirmation, failed resolution, escalation, high frustration, empty retrieval, low confidence, and follow-up questions.

Create at least one mocked multi-turn end-to-end test.

Do not modify other members' modules unless absolutely required for an integration contract.

Run pytest -q and inspect git diff/status.
